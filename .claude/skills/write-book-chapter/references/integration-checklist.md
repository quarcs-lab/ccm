# Integration checklist — keeping the book in sync

When a chapter is added, many files reference chapter numbers, the chapter list,
or the download bundles. This file lists every one and gives the exact
**append** and **insert+renumber** procedures, then the render/commit/publish
steps and the self-audit gate. Work top to bottom.

Method chapters are the numbered files `01-…qmd … 10-…qmd`. `index.qmd`
(preface) and `references.qmd` are unnumbered and never renumbered.

---

## A. Decide the chapter number

- **Append** (new last method chapter): number = current max + 1, zero-padded to
  two digits (e.g. existing max `10` → new file `11-your-slug.qmd`).
- **Insert at position N**: the new file is `NN-your-slug.qmd`; every existing
  chapter `≥ N` shifts up by one. Do the renumber in §B *before* writing.

Confirm the slug is short, kebab-case, and descriptive (matches the title), e.g.
`11-generalized-random-forests.qmd`.

---

## B. Insert + renumber procedure (skip if appending)

Inserting at position `N` when the current max is `M`. Rename from the top down so
nothing is clobbered:

```bash
# for k = M, M-1, ..., N  (highest first):
git mv 10-gsynth.qmd 11-gsynth.qmd
git mv 09-matrix-completion-and-ife.qmd 10-matrix-completion-and-ife.qmd
# ... down to position N
```

Then **rewrite every cross-reference to a shifted number.** Chapter numbers
appear in several textual forms — grep for all of them across the repo:

```bash
grep -rnE 'chapter[s]? +[0-9]|ch\.? *[0-9]|chs\.? *[0-9]|\(ch\. *[0-9]|chapter-[0-9]{2}\.zip|§[0-9]' \
  *.qmd README.md
```

For each hit that points at a renamed chapter, update the number. Pay attention
to:

- Prose references ("chapter 4", "ch. 5", "chapters 2–7", "(ch. 9)").
- The roadmap table rows and the decision-tree node labels in
  `01-introduction.qmd` (they carry "(ch. K)").
- Range statements ("Part I (chs. 1–7)", "Part II (chs. 8–10)") in `index.qmd`
  and `README.md` — the ranges move when you insert.
- `chapter-NN.zip` download references (these are auto-generated by JS from the
  filename, so the JS needs no change, but any *prose* that names a zip does).
- "previous/next chapter" phrasing in the two chapters now adjacent to the
  inserted one (their callback/hand-off must still point at the right neighbour).

Renaming a file orphans its Quarto freeze cache and `*_cache/` / `*_files/`
directories (they are filename-keyed and gitignored). That is harmless — Quarto
re-executes on the next render. Do not hand-edit `_freeze/`.

---

## C. Per-file sync (always)

Update each of these:

1. **`_quarto.yml`** — add the filename to the `chapters:` list in the correct
   position (the list is flat; order = reading order).

2. **`R/build_chapter_zips.R`** — add the filename to the `chapters <- c(...)`
   vector. The generic loop already ships `R/table_helpers.R`,
   `data/proposition99.rds`, `references.bib`, and `apa.csl` into every bundle.
   If the chapter uses a **different/extra dataset or helper**, add a per-chapter
   branch like the existing ones, e.g.:

   ```r
   if (chap == "11-your-slug.qmd") {
     file.copy("data/your_data.rds",
               file.path(stage, "data/your_data.rds"), overwrite = TRUE)
   }
   ```

   (Part II chapters ship `data/cs_minwage.rds` this way; chapter 7 ships the
   `R/scspill/` helpers and `data/california_smoking.rda`.)

3. **`index.qmd`** (preface) — add a bullet for the chapter under "Part I" or
   "Part II" matching the existing bullet style (`- **Name** — one line.`). If
   the chapter changes a Part's chapter range or the "forthcoming cross-method
   comparison" sentence, update that too.

4. **`01-introduction.qmd`** — three places:
   - **Roadmap table** (the "How each method builds `$\widehat{Y(0)}$`" table):
     add a row under the right Part subheading giving the chapter's counterfactual
     formula in book notation, e.g.
     `| {{Method}} (ch. N) | $\widehat{Y_{1t}(0)} = {{...}}$ — {{gloss}}. |`.
   - **Decision-tree mermaid**: add a node for the new method and the edge(s) that
     route to it. Slot it into the existing diagnostic logic (the first split is
     staggered-panel vs single-unit); give the node a `Cost:` line like its
     siblings. Keep the `(ch. N)` label in sync.
   - **"Roadmap of the book"** section: add the chapter to the right Part list,
     and update the Part heading's chapter range if it shifted.

5. **`README.md`** — four places:
   - The **chapter table** (`| # | Chapter | File | Status |`): add a row; if
     inserting, renumber the `#` column and any shifted file names.
   - The **Project status** line (e.g. "ten method chapters…", "Part I (chs.
     1–7)", "Part II (chs. 8–10)"): update the count and ranges.
   - The **"What the drafted chapters contain"** paragraph: extend it.
   - The **project-structure tree**: add the new `.qmd` (and any new data file).
   - If the chapter was listed under **"Next"**, remove it from that list.

6. **`references.bib`** — add the verified BibTeX entries (see house style §8).

7. **Previous chapter** — add/adjust its closing **hand-off** paragraph so it
   points to the new chapter by name and number.

8. **Next chapter** — adjust its opening **callback** so it refers to the new
   chapter as its predecessor.

9. **Part seam** — if the insertion/append changes which chapter opens Part II,
   move the `::: {.callout-note}` "Part II begins here" block to the new opener
   and update the seam paragraph at the end of the chapter before it (house style
   §9).

10. **`DESCRIPTION`** — add any new package(s) to the human-readable manifest
    (keeps RStudio's "Install Dependencies" button working).

---

## D. New dataset (only if the chapter introduces one)

- Place the cached file in `data/` (prefer `.rds`; `read_rds()` in the chapter).
- Add the data-shipping branch to `R/build_chapter_zips.R` (see §C.2) so the
  standalone bundle can render offline.
- Mention the dataset in `README.md` (the `data/` part of the tree and the status
  prose) and in `index.qmd`'s Acknowledgments if it has a distinct source.

---

## E. New R package (only if not already in renv.lock)

```r
renv::install("pkg")   # in an R session at the repo root
renv::snapshot()       # updates renv.lock
```

Then add the package to `DESCRIPTION`. Confirm `renv.lock` changed and is staged
for commit.

---

## F. Render and verify

```bash
quarto render --to html NN-your-slug.qmd   # fast single-chapter loop
quarto render --to html                     # full book — resolves cross-refs and rebuilds zips
```

- Never run a bare `quarto render` (it would build the PDF and trigger a TinyTeX
  install). Always `--to html`.
- Fix every error and every warning that leaks into the HTML. Do not silence
  modelling-chunk warnings.
- The full render reruns the `R/build_chapter_zips.R` pre-render hook; confirm
  `downloads/chapter-NN.zip` was built for the new chapter.

---

## G. Self-audit gate (before commit)

Confirm, against the rendered HTML (and `_freeze/NN-…/execute-results/html.json`
if needed):

- [ ] No `NA` / `NaN` inline numbers; no `[1] NA` in any output.
- [ ] No empty tables ("Table has no data") and no flat-zero figures.
- [ ] All prose numbers are inline R, none hardcoded.
- [ ] Notation matches the book-wide table; colliding symbols renamed + glossed.
- [ ] Displayed equations match the fitted models.
- [ ] Opening callback + closing hand-off present; Part-seam callout correct.
- [ ] After any renumber: re-run the grep from §B and confirm zero stale numbers;
      spot-check the decision tree, roadmap table, README table, and both
      neighbour chapters.
- [ ] `_quarto.yml`, `build_chapter_zips.R`, `index.qmd`, `01-introduction.qmd`,
      `README.md`, `references.bib` all updated.

---

## H. Commit and publish

```bash
quarto render --to html
quarto publish gh-pages --no-prompt --no-render
```

Git (per the skill's standing choice — commit & publish):

- If on `main`, create a feature branch first.
- Stage everything, including any `git mv` renames, `renv.lock`, and `DESCRIPTION`.
- Commit with a clear message ending in:
  `Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>`
- Publish to `gh-pages` (force-pushes the rendered `_book/`).
- `CLAUDE.md` requires the live site to stay in sync with `main`: tell the user to
  merge the branch into `main` (or offer to do it).

Report what changed: the new file, every renamed file, every synced file, new
packages, and the published URL.
